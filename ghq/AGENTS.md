# Общий порядок работы с репозиториями

Эти правила действуют для личных репозиториев внутри `~/ghq`.
Сначала прочитай инструкции конкретного репозитория. Более близкие к изменяемым
файлам правила уточняют этот порядок. Не переноси ограничения одного проекта
на остальные.

## Исключение: pvs-efs-assist, бывший Graph

Для любой копии `pvs-efs-assist`, в том числе на GitVerse и GitHub, действуют
правила закрытого сегмента из её `AGENTS.md`. Полная сборка, тесты и запуск
подтверждаются только в закрытом сегменте. Локальные проверки и независимое
ревью не заменяют этот этап. Не применяй к этому проекту требование полного
локального запуска из разделов ниже.

## 1. План

- Уточни ожидаемый результат и критерии готовности. Для простой задачи достаточно
  короткого плана; не усложняй небольшие правки.
- Проверь состояние Git и сохрани чужие или несвязанные изменения.
- Прочитай инструкции проекта и только нужные исходники. Если доступен граф
  Codebase Memory, используй его первым для поиска структуры кода и проверь
  покрытие найденных файлов. При пробелах прочитай соответствующий исходник.
- Для актуального синтаксиса библиотек и API используй Context7; если он
  недоступен, обратись к официальной документации и обозначь это ограничение.

## 2. Изменения

- Внеси минимальные достаточные изменения для решения задачи.
- Сохрани существующие настройки и поведение вне согласованной задачи.
- Не добавляй ключи, токены, пароли, личные данные и локальное состояние в Git.
- Не заменяй рабочие зависимости заглушками ради успешной проверки.

## 3. Тесты и сборка

- Определи команды проверки по документации и настройкам самого проекта.
- Сначала выполни проверки затронутого поведения. Для существенных изменений
  запусти относящиеся к задаче тесты, проверку типов, линтер и сборку, если они
  предусмотрены проектом. Полный набор нужен при широком влиянии изменений
  или по требованиям проекта.
- Добавляй содержательные тесты для нового поведения и исправленных ошибок.
  Для правок текста и других простых обратимых изменений достаточно подходящей
  проверки; не создавай тесты, которые лишь повторяют реализацию.
- При неудаче выясни причину, исправь относящуюся к задаче ошибку и повтори
  затронутые проверки. Не запускай прошедшие проверки заново без причины.
- Если проверка недоступна, укажи причину и что осталось неподтверждённым.
  Не выдавай просмотр кода за успешное выполнение тестов.

## 4. Независимое ревью

- Для существенных изменений кода используй отдельного ревьюера, если он доступен
  и передача данных ему разрешена. В настроенном OpenCode это агент `review`
  через OpenRouter; в других клиентах используй доступный разрешённый механизм.
  Не утверждай, что независимое ревью было, если выполнена только самопроверка.
- Передай ревьюеру задачу, критерии готовности, изменения и результаты проверок.
  Он должен искать конкретные ошибки, регрессии и риски, а не переписывать код.
- Основной агент оценивает замечания, исправляет подтверждённые проблемы и
  повторяет нужные проверки. При необходимости передай исправления на ревью.
- Для простых правок документации достаточно проверки смысла и оформления,
  если отдельное ревью не запрошено.

## 5. Проверка интерфейса

- Если задача меняет пользовательский веб-интерфейс, запусти приложение и
  проверь относящийся к задаче сценарий через Playwright MCP, если это возможно.
- Проверь основной сценарий, важные ошибки и состояния, а также размеры экрана,
  которые затрагивает изменение. При необходимости приложи снимок результата.
- Используй отдельную тестовую сессию. Не выполняй реальные платежи, отправку
  сообщений или изменение рабочих данных без разрешения.
- Для задач без веб-интерфейса этот этап не требуется. Недоступный запуск
  явно отметь; не заменяй реальную проверку выдуманным результатом.

## 6. Коммит, PR и CI

- Перед коммитом проверь состав и содержимое изменений на секреты и лишние файлы.
  Добавляй только относящиеся к задаче пути; чужие изменения не включай.
- Сообщения коммитов пиши коротко, на русском, только с сутью изменения.
- Создавай коммит, отправляй изменения, открывай или объединяй PR только когда
  это следует из запроса пользователя или уже выданного разрешения.
  Наличие GitHub MCP само по себе такого разрешения не даёт.
- Для разрешённого PR кратко опиши проблему, результат и выполненные проверки.
  После отправки проверь предусмотренный проектом CI. Не считай задачу полностью
  проверенной, пока обязательные проверки не завершены; сообщи об их состоянии.
- Соблюдай правила веток, канонического сервера и зеркал конкретного репозитория.
  GitHub MCP используй для GitHub; для других серверов — подходящие инструменты.
  Не создавай внешние комментарии и сообщения без разрешения.

## Навыки Matt Pocock

Набор `mattpocock/skills` установлен для Codex, Claude Code и OpenCode.
Используй навыки по задаче, а не весь набор для каждой правки. Название команды
может иметь префикс плагина; выбирай доступный навык по его имени.

- `grill-with-docs` — для неоднозначной или крупной задачи: уточнить требования,
  термины и решения. Не устраивай обязательный опрос для понятной небольшой правки.
- `diagnosing-bugs` — воспроизвести ошибку, проверить гипотезу, исправить причину
  и подтвердить результат. Не меняй код наугад.
- `tdd` — для проверяемого поведения: падающий тест → минимальное исправление →
  улучшение кода. Не требуй выполнения тестов там, где закрытый SDK недоступен.
- `implement` — выполнение согласованной задачи. Даже если навык предлагает
  коммит в конце, соблюдай раздел «Коммит, PR и CI»: поручение на реализацию
  само по себе не разрешает коммит, отправку или публикацию.
- `code-review` — проверить соответствие требованиям и стандартам. Зафиксируй
  базовую точку сравнения; явно включи нужные незакоммиченные изменения,
  если проверяется рабочая копия. Не называй ревью независимым только из-за
  запуска навыка. В OpenCode независимую модель предоставляет агент `review`
  через OpenRouter, которому передают задачу, diff и результаты проверок.
- `handoff` — передать работу между чатами, машинами или в закрытый сегмент:
  цель, ветка/коммит, изменения, проверки, ограничения и следующий шаг.
  Не включай секреты, закрытые SDK и неразрешённые исходные логи.
- `to-spec`, `to-tickets`, `triage`, `pr` — применять по необходимости; сначала
  подготовить локальный результат, а публиковать только по разрешению.
- `retro` — после сложной задачи предложить конкретное улучшение процесса,
  не переписывая окружение без согласованной задачи.

Перед первым использованием инженерных навыков в конкретном репозитории
проверь их настройку: трекер задач, термины и расположение документации.
Если настройки нет, используй `setup-matt-pocock-skills` для этого репозитория
с учётом уже существующих документов. Не запускай настройку сразу для всех
репозиториев и не создавай задачи, метки или внешние комментарии автоматически.
До выбора трекера готовь материалы локально; наличие GitHub-зеркала не делает
его автоматически основным трекером. Не дублируй существующие ADR и глоссарии.

Правила проекта, ограничения передачи данных и прямые указания пользователя
применяются и при использовании навыков. Для `pvs-efs-assist` полные проверки
остаются в закрытом сегменте; навык не отменяет это ограничение. При передаче
задачи другому агенту явно передай относящиеся к задаче ограничения и критерии.

## Готовность и отчёт

Задача готова, когда выполнены её критерии, пройдены обязательные доступные
проверки и разобраны подтверждённые замечания. PR и отправка не обязательны,
если пользователь их не поручал.

В итоговом ответе коротко укажи: что изменилось, что проверено, что осталось
неподтверждённым и созданы ли коммит, отправка или PR. Пиши понятно и по-русски,
если пользователь не попросил другой язык. Не скрывай ограничения проверки.
